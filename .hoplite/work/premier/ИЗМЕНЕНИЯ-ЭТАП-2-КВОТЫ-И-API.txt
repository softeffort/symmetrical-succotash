Квоты, списания и публичный API (2026-11-20) — этап 2 плана

Основа — архив 5714.zip (этапы 0, 1 и 3). Сделаны все 28 строк этапа 2: BIZ-06, 07, 08, 10, 14, 15, 17, 18, 19, 20, 21,
22, 23, 24, 28, 35, 38 и API-01 … API-11. Меняются серверные файлы, тесты и одна строка в скрипте папки
на страницах чата.
В базе появляются две новые таблицы — ultra_days (суточные итоги Ultra) и api_key_spend (расход ключей API);
они создаются сами при запуске. Итоги Ultra один раз заполняются из старых журналов (автоматически).

Главное: каждое списание теперь оставляет квитанцию — сутки по Москве, источник (дневной лимит, пакет, бонус, сброс,
кредиты Ultra) и сумму. Возврат идёт по квитанции. Решение «оставить списание или вернуть» принимается в одном месте
(billing.js, settle) и одинаково для веб-чата и API.

Б. Публичный API

18. Пересчёт доплаты Ultra и предел ключа (API-01). billing.js, api/gateway.js.
   Было: пересчёт доплаты после ответа мог вывести расход ключа за его суточный предел кредитов (ultra_cap).
   Теперь: в пересчёт передаётся остаток предела ключа за сутки списания; сверх предела не списывается.
   Запрос, который начался до полуночи по Москве и закончился после, не получает свежий предел. Проверено шестью
   одновременными запросами: расход ключа равен пределу, следующий запрос получает 429.
19. Ошибки поставщика (API-02). api/native.js (новый), api/upstream.js, api/gateway.js.
   Было: в прямом (native) режиме события ошибок шли клиенту как есть — с ключом или адресом поставщика в тексте.
   Теперь: событие с ошибкой собирается заново только из разрешённых полей — соседние поля поставщика (debug
   и подобные) клиенту не уходят. Из текста ошибок вырезаются ключи и адреса всех моделей, IP-адреса, домены,
   длинные токены. Из остальных событий и ответов ключи и адреса поставщиков вырезаются по точному значению
   в любой строке на любой глубине. Ошибки авторизации, доступа и оплаты у поставщика клиент видит как общую
   ошибку сервиса, а администратор получает оповещение. Ошибка в теле ответа «200» становится 502.
   В событии response.failed поле id передаётся, только если оно похоже на идентификатор и не содержит секрета;
   причина незавершённого ответа — только из известного списка (max_output_tokens, content_filter).
20. Обрыв прямого потока (API-03). api/native.js, api/gateway.js.
   Было: поток без финального события считался успехом.
   Теперь: сервер ждёт финальное событие протокола. Без него клиент получает ошибку в формате своего протокола,
   в журнале — 502 и отметка «не завершён», списание возвращается по политике (пункт 13), той же, что в веб-чате:
   получено меньше 200 знаков — возврат, больше — списание остаётся. Правило одно для прямого режима
   и режима перевода. Считается только то, что реально отправлено клиенту: размышления модели, которые клиент
   не просил (Messages без thinking), доставленным текстом не считаются.
21. Пустой ответ (API-04). api/native.js.
   Было: пустой блок в начале ответа считался доставкой — списание не возвращалось.
   Теперь: доставка — это непустой текст или размышление, законченный вызов инструмента с именем и аргументами,
   либо элемент ответа с содержимым.
22. Память на запрос (API-05). api/util.js, api/upstream.js, api/gateway.js.
   Было: место в бюджете памяти освобождалось сразу после чтения тела; ответ поставщика не ограничивался.
   Теперь: резерв держится до конца ответа и растёт на байты ответа поставщика. Пределы тел: 64 МБ на человека
   и 128 МБ на весь процесс (как раньше); сверх — 429 своему и 503 чужому. Один запрос проходит всегда.
   Ответ поставщика ограничен 32 МБ (API_RESPONSE_MAX_MB): поток, обычный ответ и текст ошибки (256 КБ).
   Потоковые ответы (SSE) тоже занимают место в бюджете, пока идут. Первый 1 МБ каждого ответа в бюджет
   не идёт (API_RESPONSE_FREE_KB) — обычные ответы от чужих запросов не зависят. Рост сверх 1 МБ занимает
   бюджет по тем же правилам, что и тело: места нет — этот запрос получает ошибку (429 или 503; в идущем
   потоке — событие ошибки), списание возвращается по политике. Память под ответы ограничена: бюджет плюс
   1 МБ на каждый запрос в работе.
23. Имена инструментов (API-06). api/convert.js.
   Было: инструменты из разных пространств имён могли получить одно имя; tool_choice не переводился.

   используется в списке инструментов, в истории и в tool_choice. tool_choice на несуществующий инструмент — 400.
24. reasoning.effort (API-07). api/convert.js, api/gateway.js.
   Было: значение молча терялось.
   Теперь: none, minimal, low, medium, high, xhigh передаются поставщику; другое значение — 400 до списания.
25. stop_sequence (API-08). api/output.js.
   Было: stop_sequence в ответе угадывался.
   Теперь: указывается, только если поставщик сам назвал сработавшую последовательность; иначе end_turn.
26. Серверные инструменты (API-09). api/convert.js, api/gateway.js.
   Было: неподдерживаемые серверные инструменты (web_search и другие) молча убирались из запроса.
   Теперь: такой запрос получает 400 (код unsupported_tool) до списания. Прежнее поведение включается

27. Повторы запросов к поставщику (API-10). api/upstream.js.
   Было: после сетевой ошибки запрос повторялся — поставщик мог выполнить и посчитать его дважды.
   Теперь: каждый запрос несёт ключ идемпотентности (Idempotency-Key). Повтор после неясной сетевой ошибки
   или ответа 5xx (500, 502, 503, 504) — только если запрос точно не ушёл (нет соединения, не найден адрес)
   или поставщик отмечен как поддерживающий ключ идемпотентности. Иначе клиент получает ошибку с разрешением
   повторить (x-should-retry).
28. Суточные лимиты ключа (API-11). api/usage.js, api/index.js, api/gateway.js.
   Было: лимиты ключа считались по журналу запросов; потерянная запись журнала давала лишний расход.
   Теперь: расход ключа ведётся отдельным счётчиком (таблица api_key_spend) в одной транзакции со списанием.
   В день обновления счётчик стартует с того, что уже записано в журнале за эти сутки, — лимит не обнуляется.
   Потерянная запись журнала — оповещение администратору «API журнал запросов: запись потеряна».

Новые настройки (все необязательные; значения по умолчанию подходят)
- STREAM_END_CHECK=off — выключить проверку конца потока в веб-чате (пункт 5), если поставщик не присылает
  ни [DONE], ни finish_reason.
- API_RESPONSE_MAX_MB — предел ответа поставщика в API, по умолчанию 32.
- API_RESPONSE_FREE_KB — сколько килобайт каждого ответа API не идёт в бюджет памяти, по умолчанию 1024 (пункт 22).
- API_DROP_SERVER_TOOLS=1 — молча убирать серверные инструменты, как раньше (пункт 26).
- API_IDEMPOTENT_HOSTS — список хостов поставщиков через запятую, которые поддерживают Idempotency-Key (пункт 27).
  То же для одной модели: поле idempotent: true в настройках модели.
- API_IDEMPOTENCY_KEY=off — не отправлять заголовок Idempotency-Key.

Что важно знать
- Codex CLI по умолчанию присылает инструмент web_search и после обновления получит 400 (пункт 26).
  Два выхода: web_search = "disabled" в настройках Codex у пользователя или API_DROP_SERVER_TOOLS=1 на сервере.
  Если Codex у ваших пользователей — основной клиент, включите API_DROP_SERVER_TOOLS=1 до перезапуска.
- Память процесса (проверка этапа). Бюджет считает байты тел запросов. Сам процесс держит на каждое принятое тело
  несколько копий: буфер, строку, разобранный JSON, запрос к поставщику. Замер на тесте: 12 одновременных запросов
  по 24 МБ — принято 4 (96 МБ), остальные получили отказ; пик памяти процесса вырос примерно на 500–570 МБ,
  то есть около 5–6 размеров принятых тел. При настройках по умолчанию (128 МБ тел) пик может дойти примерно
  до 750 МБ сверх обычной памяти. Если памяти на сервере меньше — уменьшите API_BODY_INFLIGHT_MB (например, 64).
- Отступление в пункте 8: план требовал хранить десятые целыми числами. Сделано иначе: значения хранятся прежним
  форматом (0.3, 1.7), но округляются до десятых при каждом изменении. Результат тот же, перенос данных не нужен.
- Пункт 13: порог «заметная часть ответа» — 200 знаков, как было раньше для отмены.
- API, изменение для клиентов (пункты 13 и 20): сбой или обрыв потока после короткого текста (меньше 200 знаков)
  теперь возвращает списание. Раньше любой первый знак оставлял запрос списанным. Отмена клиентом после первого
  текста по-прежнему остаётся списанной.
- API, изменение для клиентов (пункт 27): сервер больше сам не повторяет запрос после ответа поставщика 500 или 503
  (как и 502, 504), если поставщик не отмечен как идемпотентный. Клиент получает ошибку с x-should-retry и
  повторяет сам; SDK OpenAI и Anthropic делают это автоматически. Чтобы вернуть повторы на сервере, отметьте

- Пункт 19: вырезание по точному значению не ловит ключ, разрезанный между двумя событиями потока. Если модель
  сама напишет в ответе адрес поставщика, он тоже заменится на [redacted].
- Пункт 22: пока большие ответы пользователя занимают весь его бюджет (64 МБ), его новые большие запросы
  получают 429, а его идущий ответ, который растёт сверх 1 МБ, может получить ошибку «holds too much memory».
  То же для общего бюджета (128 МБ) — 503 «no memory left for this response». Запрос, который идёт один,
  не ограничивается (кроме 32 МБ на ответ). При настройках по умолчанию это возможно только при очень больших
  одновременных ответах.
- Пункт 6: при исчерпанном лимите сайтов не отдаётся любой блок ответа, который сервер считает сайтом

- Пункт 3: при перезапуске сервер ждёт запросы API (/v1) до SHUTDOWN_GRACE_MS (как раньше), затем обрывает
  их и останавливает ответы веб-чата. Ответы веб-чата срок не продлевают. На расчёт даётся до 3 с; что
  не остановилось — рассчитывается принудительно: незакрытые резервы возвращаются, ответ считается остановленным

- Пункт 11: stream_options.include_usage отправляется только моделям Ultra. Если поставщик не прислал число
  токенов, остаётся оценка. Служебные повторные запросы сервера (починка файла) пользователю не списываются.

- Пункт 25: stop_sequence появляется только с подтверждением поставщика. Клиент, который ждал это поле

- Незавершённые ответы в момент обновления: списания, сделанные до перезапуска, остаются как есть;
